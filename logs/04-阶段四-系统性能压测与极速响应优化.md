## 一、阶段目标与产物

### 1.1 目标（对齐 README Step 12–13 + 评分「体验性 20%」）

在**不牺牲安全围栏语义、不破坏既有 pytest / EX 评测可复跑性**的前提下，把端到端响应从「分钟级合规」推进到可演示的体验目标：

| 查询档位 | 规划体验目标（答辩口径） | 阶段三基线（全量 7 题） | 本阶段期望 |
|----------|--------------------------|------------------------|------------|
| 简单（单表/少表、重复或相似问） | **秒级**，命中缓存时 **毫秒～亚秒** | 多数题 2–5s（含失败题） | 冷路径仍秒级；热路径显著下降 |
| 中等 / 复杂（多表多指标、跨主题域） | **十秒级内**（远优于「分钟级」） | 同上量级（瓶颈多为 LLM） | 分阶段计时定位瓶颈；并行/拆解对可拆查询有效 |
| 赛题底线 | 分钟级内完成 | **已满足**（p95≈5s） | 用压测报告固化证据，避免「感觉快」 |

> **重要现实**：当前端到端耗时已远低于「分钟级」。瓶颈几乎肯定在 **LLM 生成 / 1-Shot 纠错**，而非 DuckDB。本阶段价值是：（1）可解释的分阶段耗时；（2）重复/相似问与元数据加载的缓存；（3）对可拆复杂查询的并行；（4）可复现压测报告支撑答辩「体验性」。

### 1.2 交付产物


| 交付物 | 对应 README | 验收要点 |
|--------|-------------|----------|
| Pipeline 分阶段计时 | Step 12/13 前置 | `ask()`（或包装层）输出 prune / generate / L1 / L2 / execute / probe 各段 ms；评测报告可汇总 |
| 元数据与剪枝缓存 | Step 12 | `load_metadata` / 剪枝结果可复用；重复加载与同问剪枝不再付全价 |
| 问数结果 / SQL 缓存 | Step 12 | 精确匹配（及可选规范化相似键）命中时跳过 LLM，毫秒级返回；可开关、可失效 |
| 复杂查询并行（或等价提速） | Step 13 | 对「客户筛选 ∩ 多指标」类路径：子集拆解后并行执行再合并；有单测与对比计时 |
| 压测脚本与报告 | — | 固定问句集（冒烟 + 可选金标）冷/热路径对比；p50/p95；写入 `logs/perf_reports/` |
| CLI / Demo 入口 | — | `querypilot bench` 或 `scripts/bench_pipeline.py`；一键出表 |

**本阶段不做**：Chat UI / HTTP API 产品化（阶段五）；正式冲 >90% EX 的全量准确率战役（阶段五 Step 15，但可用阶段三工具并行小步提准）；引入重型分布式任务队列。

**须遵守约定**：跨表默认只按 `pty_id`/`org_id` Join；只读 DuckDB；不改 `data/`；Agent 仍经 `load_metadata()` / `ask()`；缓存不得绕过 L1 对「新生成 SQL」的校验（命中「已校验通过」的缓存条目时可跳过重算，但条目本身须来自曾通过围栏的路径）。

### 1.3 成功标准（可验证）


| # | 成功标准 | 验证方式 |
|---|----------|----------|
| S1 | 分阶段计时字段齐全，假 client 单测不依赖真实 LLM | `pytest` 覆盖 timing 模型与聚合 |

### 2.3 与准确率工作的边界（务必分清）

> **历史注记**：阶段三首轮基线曾为 EX **1/7 = 14.3%**。续一/续二后官方默认 **7/7**、Extra-A fs3 **36/36**、Extra-B fs0 **34/36**——提准穿插（剪枝召回等）已基本完成。阶段四仍**只验收体验/缓存/并行**，不冲剩余 Hard 缺口。

| 工作流 | 主责阶段 | 本阶段态度 |
|--------|----------|------------|
| 剪枝漏表 / Prompt / 口径 / Few-Shot | 续一/续二已收口 | 步骤 2–5 **不再排**提准战役；回归抽测即可 |
| 精确 Few-Shot 短路（续一） | 阶段三 HITL | 与步骤 3 问数缓存**并存**；缓存键须含 `few_shot_version` / metadata 版本 |
| Redis / 并行 / bench 报告 | **阶段四主线** | 必须交付 |
| 盲测打包 + UI | 阶段五 | 本阶段不打包 |

**原则（AGENTS.md）**：缓存与并行用最少代码解决问题；默认 **进程内缓存** 即可支撑原型与答辩。Redis 作为**可选后端**（配置开关），不强制本机起 Redis 才能跑通测试。

### 步骤 1：分阶段计时与压测脚手架

**解决什么问题**

阶段三只有 `ask` 整段耗时，无法证明瓶颈在 LLM 还是剪枝/DB，优化会盲目。

**具体做法**

1. 在 `pipeline.ask()` 各阶段打点：`prune` → `generate` → `l1` → `l2` → `execute` → `probe`。
2. 扩展结果模型，例如：

```text
StageTiming:
  prune_ms, generate_ms, l1_ms, l2_ms, execute_ms, probe_ms, total_ms
  cache_hit: bool = False
```

3. `Eval` 侧：若 `PipelineResult` 已带细分，则 `TimingInfo` 对齐填充；保持旧字段兼容。
4. 新增 `scripts/bench_pipeline.py`：
   - 输入：问句列表（内置 5 条冒烟 + 可选 `--from-qa`）
   - 模式：`--cold`（清缓存）/ `--warm`（同句再跑）/ `--rounds N`
   - 输出：JSON + 控制台表（p50/p95、分阶段均值）

**涉及文件**：`agent/pipeline.py`、`agent/models.py`、`eval/models.py`（可选）、`scripts/bench_pipeline.py`、`tests/test_pipeline_timing.py`

**验证**

```powershell
pytest tests/test_pipeline_timing.py -q
python scripts/bench_pipeline.py --limit 2 --cold
# 报告含 prune_ms / generate_ms / … 字段
```

### 步骤 2：元数据与 Schema 剪枝缓存

**解决什么问题**

`load_metadata()`（含可选读 DuckDB 编码）与剪枝在多题批跑时重复付费；批评测与 Demo 首包延迟可降。

**具体做法**

1. `metadata_cache`：进程内单例或 LRU，键 = `metadata_dir` 路径 + 关键文件 mtime/hash；提供 `get_metadata()` / `invalidate_metadata()`。
2. 剪枝缓存：键 = `normalize(question) + metadata_version` → `PrunedSchema` 序列化或对象引用（同进程）。
3. `ask()` / `run_eval` 默认走缓存获取 metadata；单测可用 `invalidate` 或 `cache=False` 保证隔离。
4. **不**缓存「未通过校验的元数据」；校验失败不写入。

**涉及文件**：`querypilot/cache/*`、`metadata_engine/bundle.py` 或 `agent/pipeline.py` 调用点、`config.py`、`tests/test_*cache*`

**验证**

```powershell
pytest tests/test_cache_keys.py tests/test_query_cache.py -q -k "metadata or prune"
# 二次 load / 同问 prune 耗时显著下降（断言或 bench 打印）
```

### 步骤 3：高频问数 SQL / 结果缓存（README Step 12）

**解决什么问题**

重复演示同一营销问句时不应每次打 DeepSeek；热路径应接近「读缓存 + 可选再执行」。

**具体做法**

1. **缓存键**：`normalize(question)` + `max_rows` + `few_shot_version` + `metadata_version`（避免回流后脏读）。
2. **缓存值**（建议两级，由简到繁）：
   - L1：`sql` + `tables` + `rationale`（命中后仍可 `execute`，保证数据新鲜）
   - L2：可选缓存 `rows`（仅 Demo/bench；默认关闭或短 TTL，避免「结果过期」争议）
3. **写入条件**：仅当本次 `ask` 成功且 L1/L2 通过（`ok=True` 且非危险降级）时写入。
4. **绕过**：`ask(..., use_cache=False)`；CLI `--no-cache`；环境变量 `QUERYPPILOT_CACHE=0`。
5. **Redis（可选）**：同一接口，`MemoryStore` / `RedisStore` 实现 `get/set`；无 Redis 时自动回退 Memory，测试不依赖外进程。
6. CLI 输出增加 `cache_hit=yes|no`，便于答辩演示。

**涉及文件**：`cache/query_cache.py`、`cache/memory.py`、（可选）`cache/redis_store.py`、`agent/pipeline.py`、`cli.py`、`tests/test_query_cache.py`

**验证**

```powershell
pytest tests/test_query_cache.py -q
python scripts/bench_pipeline.py --limit 1 --warm
# 期望：warm total_ms 远小于 cold；cache_hit 为 true
```

**与安全的关系**：缓存命中的是「已经围栏放过的 SQL」；若只缓存 SQL 再执行，仍走只读 `execute`。不要对用户任意新 SQL 免检。

### 步骤 4：复杂查询并行拆解（README Step 13）

**解决什么问题**

跨主题域多指标时，串行大 SQL 或「先错后纠」耗时长；将「客户子集」与「指标聚合」拆开可利用 DuckDB/多线程并行，并缩小单次 LLM 规划难度（可选）。

**范围控制（防过度设计）**

本阶段只做 **一种默认策略**，不做通用分布式执行器：

| 模式 | 触发条件（示例启发式） | 行为 |
|------|------------------------|------|
| A. 执行层并行 | 已有单条合法 SQL，且可静态拆成多个只读子查询（少见，慎用自动改写） | 暂不优先 |
| B. 计划层两段式（推荐） | 问句同时强匹配「客群筛选」+「≥2 个指标域」（资产/交易/持仓等） | ① LLM 或规则生成「客户 pty_id 子集 SQL」② 对每个指标域并行 `execute` 聚合 ③ 按 `pty_id` 合并 |
| C. 批评测并行 | `run_eval` 多题之间 | 线程池并行多题（注意 DuckDB 连接是否线程安全；可每线程一连接）——对「体验单题延迟」无帮助，但对「出报告墙钟时间」有用，可作加分项 |

**推荐落地顺序**：先做 **C（评测墙钟并行）** 或 **B 的最小版**（固定模板：子集 CTE + 并行指标查询），用 1 个构造用例证明正确性与耗时对比；避免一上来做自动 SQL 重写。

**具体做法（B 最小版）**

1. `parallel.py`：`split_customer_filter_and_metrics(question, pruned)` → 两个子任务描述（可先规则，不强制二次 LLM）。
2. `concurrent.futures.ThreadPoolExecutor` 并行 `execute` 两个只读 SQL（各自经 L1，共享 metadata）。
3. `merge_on_pty_id(df_a, df_b)` → 最终表；失败则 **回退原单次 SQL Pipeline**（正确性优先）。
4. 计时标记 `parallel=True` / `fallback=True`。

**涉及文件**：`querypilot/agent/parallel.py`、`pipeline.py` 可选分支、`tests/test_parallel_query.py`、bench 对比开关 `--parallel`

**验证**

```powershell
pytest tests/test_parallel_query.py -q
python scripts/bench_pipeline.py --question "..." --parallel --cold
# 与 --no-parallel 对比 total_ms；结果行集合一致（或文档约定的可接受差异）
```
