## 一、背景：三个递进的问题

1. **一次 ask 是否是标准 Agent 工作流程？**
2. **本项目与赛题要求的「取数 Agent」是什么关系？是否背离赛题？**
3. **如何吸收更多 Agent 优势，在更像 Agent 的同时提升性能？**

结论速览：

- 一次 ask **不是**标准 Agent 循环，而是确定性编排的 staged pipeline：`prune → generate → L1 → L2 → execute → probe`，全程 LLM 调用 ≤2 次（生成 + L2 定向纠错各 1 次），无循环、无记忆、无模型决策权。
- **功能上不背离赛题**（元数据、NL→SQL、安全围栏、自动化评测全部落地）；形式上有意偏离 tool-based Agent，且项目已有论证（`logs/Summary.md` §2.6：命题方 Tool 方案「耗时长、复杂题需多轮交互」，本项目刻意改为「本地隐式检索剪枝 + 单次 LLM SQL + 双层确定性围栏」）。
- 本项目属**弱 Agent**（感知-行动系统），**不满足强 Agent 的 5 条判据**；可通过「按需 Agentic」方案补齐，且不牺牲快路径性能。

## 二、Agent 定义的三个层次

### 层次 1：学术广义定义（弱 Agent）

Russell & Norvig《人工智能：一种现代方法》：**agent = 通过传感器感知环境、通过执行器作用于环境的任何实体**。此定义下 `if-else` 函数、SQL 执行器都算 agent。本项目当然是 agent（感知问句 → 返回结果集）。

### 层次 2：行业强定义（强 Agent / Agentic）

OpenAI / Anthropic 等对 agentic system 的通行描述，拆为 **5 条判据**：

| # | 判据 | 含义 |
|---|------|------|
| A | **模型拥有决策权** | LLM 决定「下一步做什么」，而非代码决定 |
| B | **工具调用循环** | 模型主动调用工具、拿到观测结果、再决定下一步（plan→act→observe 迭代） |
| C | **迭代直到完成** | 允许 N 步推理/尝试，直到自认完成或给出放弃理由 |
| D | **记忆/状态** | 跨步骤、甚至跨会话保留上下文（对话历史、长期记忆） |
| E | **反思/自主纠错** | 模型根据结果自我评估、主动修正策略 |

### 层次 3：竞赛语义

赛题全文从未定义 Agent 范式，只要求「**取数 Agent 原型系统**」（可运行系统 + AI 友好元数据 + 安全围栏 + 自动化评测），并点名建议「**另外子 agent** 进行 SQL 评价打分」。属**弱 Agent 语义**——交付的是系统能力，不是某种架构。

## 三、本项目现状：与强 Agent 判据的对照

| 判据 | 本项目实况 | 是否达标 |
|------|-----------|----------|
| A. 模型拥有决策权 | `ask()` 每步由 Python 硬编码调用；LLM 只出现在 2 个固定位置（生成、纠错），输出 JSON 后被代码接管 | ❌ |
| B. 工具调用循环 | 无工具注册表；prune/L1/L2/execute 由代码按固定顺序调用，均为单发；无 observe→re-plan | ❌ |
| C. 迭代直到完成 | 「只尝试一次」写死在代码与 prompt 中（`_MAX_CORRECTION_ATTEMPTS = 1`）；失败即降级返回 | ❌ |
| D. 记忆/状态 | 无对话历史、无 session、无长期记忆；`cache/query_cache.py` 是**结果缓存**而非记忆；每次 ask 完全无状态 | ❌ |
| E. 反思/自主纠错 | 无模型自我评估环节；结果探针是确定性规则（空结果/计数为 0/量级异常），生成提示但不改变执行 | ❌ |

**5 条全不达标。** 准确定位：**确定性编排的智能管道（deterministic orchestrated pipeline），LLM 作为受限生成子模块嵌入其中**。README 中「高性能 Agentic Engine」的 Agentic 一词，从强定义看不成立。

### 仅有的「agent 味」环节（以及为什么仍不算）

1. **L2 的 1-Shot 纠错**：EXPLAIN 报错 → 报错喂回 LLM → 修正。是最小的「观测失败 → 行动修正」闭环，但方向由代码指定、只允许 1 次、无策略选择。属**受控的异常恢复**，不是自主迭代。
2. **Eval-Agent**：启发式归因 + 可选 1 次 LLM 精修。比主 pipeline 更「agent」一点，但同样是一次判定 + 至多一次精修，无循环、无记忆。属**离线分析器**。
3. **结果探针**：检测空结果/异常量级并给出放宽建议。属**感知环境反馈**，但反馈不回流到模型，流程即结束。

共同特征：**闭环被代码写死为单步，反馈从不进入模型决策**——这正是「管道」与「agent」的分界线。

## 四、两种取数设计优劣比较（按赛题评分权重）

- **方案 A（本项目）**：确定性管道。剪枝（代码）→ 单次 LLM 生成 → 确定性围栏（L1 AST + L2 EXPLAIN + 至多 1 次定向纠错）→ 执行 → 探针。
- **方案 B（强 Agent）**：模型主导的工具调用循环。模型自主规划 → 调用工具（查元数据/查表/EXPLAIN/执行）→ 观察 → 调整 → 迭代至完成。

| 维度（权重） | 方案 A（本项目） | 方案 B（强 Agent） | 胜者 |
|---|---|---|---|
| **准确率 (30%)** | 从源头压缩幻觉空间：剪枝只给合法表列、Few-Shot 精确回流、L1 列名模糊修正、L2 定向纠错、确定性口径修正（`topn_fix`/`pnl_fix`）；每步可复现，金标 7/7 + Extra 泛化轨已实测 | 自主查证：模型可主动核验 join/枚举口径，对未见过组合更稳；但路径不固定、方差大，每轮都可能引入新错误 | **A 略胜**（封闭域内压缩幻觉空间优于自主探索；B 的优势在开放域） |
| **延迟 (20%)** | 冷路径 ≈ 1 次 LLM 生成（秒级）+ 毫秒级确定性步骤；热路径缓存毫秒级；轻松满足赛题「分钟级」 | 每步工具调用 = 1 次 LLM round-trip + 工具执行；复杂题 3–5 轮即 3–5 倍延迟，且路径随机难缓存 | **A 完胜** |
| **安全性 (攻关2)** | 围栏确定、可证明：L1 一定拦截写操作/未授权表，L2 一定拦截不可执行 SQL，与模型行为无关 | 需工具层强制兜底，但模型自主决策引入不可证明性——最终仍绕回确定性围栏 | **A 胜** |
| **可评测性 (攻关3)** | 确定性 DAG：输入→输出一一对应，EX 公平、失败可归因到 stage、问句级缓存命中率高 | 路径随机：同题多次结果不同，方差大；失败难归因（规划错还是工具错？）；缓存基本失效 | **A 完胜** |
| **可运营性 (攻关1)** | 元数据 YAML 一次性维护，代码规则可审计、可版本化；满足赛题「可持续运营」原话 | 运营负担转移到工具描述 + 模型调用习惯，成本高且隐蔽 | **A 胜** |
| **复杂查询处理** | CTE 鼓励 + 确定性修正 + `parallel.py` 规则拆解（注意：拆解是规则，不是模型规划） | 模型自主规划拆解，灵活性强；但质量依赖模型能力，弱模型拆错即连环错 | **B 胜（灵活）/ A 胜（可控）** |
| **需求模糊时** | 无澄清机制：单轮即答，含糊则错答或探针提示放宽条件 | 可多轮追问澄清；但赛题明确把「多次交互」列为痛点 | **B 胜（体验），与赛题目标冲突** |
| **成本** | 每问 1–2 次 LLM 调用，低且可预估 | 3–5 次起，2–3 倍成本，不可预估 | **A 胜** |
| **创新性 (30%)** | 「隐式检索替代工具调用」直接回应命题方痛点；EX + Eval-Agent 归因闭环是赛题点名建议 | 跟随命题方已有 Tool 方案，无增量创新，且撞上命题方自认的延迟问题 | **A 胜** |

**结论**：在赛题封闭域（9 张表、固定口径、有金标评测、分钟级指标、延迟占 20% 分）下，**方案 A 在 8/10 维度占优或持平**；方案 B 仅在「复杂查询灵活度」与「模糊需求澄清」占优，后者还与赛题目标直接冲突。方案 A 不是「背离 agent 的妥协」，而是给定约束下的正确工程取舍——用可复现性换取准确率、延迟、安全、评测四方面的确定性。

方案 B 的主场：**开放领域**（schema 动态变化）、**需求模糊需澄清**（对话产品）、**长链路任务**（取数后生成报表/发邮件等跨系统操作）——均非本赛题。

## 五、提升方案清单：按需 Agentic（Agentic-on-Demand）

### 核心原则

**确定性快路径永远优先，Agent 深度只在「失败 / 复杂 / 模糊」时按需启用。** 任何方案若让每条请求都变慢，即违背赛题 20% 延迟分。

```
默认路径（现状）: 剪枝 → 单发生成 → 围栏 → 执行        —— 毫秒~秒级，占请求绝大多数
Agent 路径（新增）: 只在 检测到复杂 / 失败 / 低置信 时触发 —— 多花的时间只花在该花的请求上
```

### A. 决策权与规划类（补判据 A/B）

**方案 1：复杂度路由（Intent Router）**

| 项 | 内容 |
|---|---|
| 做法 | 入口加轻量分类器（embedding 相似度或关键词，**不要**用大模型分类以免加固定延迟），把问句分为 简单（单表单指标）/ 中等（多表单指标）/ 复杂（跨域多指标），不同档位走不同深度 |
| 更像 agent | 系统首次获得「决定走哪条路」的决策权（判据 A 雏形） |
| 性能收益 | 简单问句（占多数）走最短路径延迟更低；复杂问句额外开销被隔离 |
| 落点 | `cli.py` / `api/routes.py` 加 mode 参数；`ask()` 加档位分支 |
| 成本 | 低 |

**方案 2：模型级规划-执行（Plan-then-Execute）**

| 项 | 内容 |
|---|---|
| 做法 | 把 `parallel.py` 的规则拆解升级为「模型规划 + 代码执行」：复杂问句先让 LLM 输出规划 JSON `{sub_queries, merge_key: "pty_id"}`，代码校验规划（表/列合法性）后**并行执行子查询**再合并；规划失败自动回退现路径（fails closed，与现有 fallback 一致） |
| 更像 agent | 真正的 plan→act 分层（判据 A+B）：模型拆解意图，代码当执行器 |
| 性能收益 | 复杂多指标查询由「串行一条大 SQL」变「并行子查询 + 合并」；子查询更聚焦、少写错 join |
| 落点 | 新模块 `agent/planner.py`，复用 `parallel.py` 合并逻辑 |
| 成本 | 中（规划 +1 次 LLM 调用，仅复杂档位启用） |

### B. 循环与反思类（补判据 C/E）

**方案 3：失败反思-重生成循环（Reflect-and-Regenerate）** ⭐ P0 首选

| 项 | 内容 |
|---|---|
| 做法 | L2 失败时，让 LLM 先**自检归因**（「错在 schema？join？谓词？聚合？」，对照剪枝 Schema），再带归因定向重生成，最多 2–3 次、成功即停。把现有「1-Shot 纠错」升级为「带反思的短循环」 |
| 更像 agent | 反思（判据 E）+ 迭代直到完成（判据 C） |
| 性能收益 | 失败转化为恢复机会 → 准确率提升；**只在失败路径触发，成功路径延迟零变化** |
| 落点 | `l2_explain.py` 的 correction 抽出为 `agent/reflect.py`；`_MAX_CORRECTION_ATTEMPTS` 1→2~3 |
| 成本 | 低，性价比最高 |

**方案 4：多候选生成 + 自洽选择（Self-Consistency）**

| 项 | 内容 |
|---|---|
| 做法 | 生成阶段并发调 2–3 个候选（不同 temperature / 不同 few-shot 子集），全部过 EXPLAIN 后以「多数一致 + 确定性探针打分」选最优 |
| 更像 agent | 多次尝试 + 选择最优（判据 C 另一种形态） |
| 性能收益 | 自洽投票是业界公认提准手段；**墙钟延迟几乎不变**（并发取最慢者），代价是 token ×2–3——契合「分钟级」指标下压准确率的诉求 |
| 落点 | `sql_generator.py` 用 `ThreadPoolExecutor` 并发；选择器 `agent/selector.py` |
| 成本 | 中（token 成本升、延迟不升；需记录选中条目保可复现） |

**方案 5：结果探针→模型反馈闭环（Probe Feedback Loop）**

| 项 | 内容 |
|---|---|
| 做法 | 探针触发（空结果/计数为 0/量级异常）时，把探针信息 + 放宽建议**喂回 LLM 重新生成一次**；仍异常才返回带提示结果 |
| 更像 agent | 观察环境反馈 → 采取行动（判据 B 完整闭环） |
| 性能收益 | 「死胡同空结果」变成一次挽救，准确率与体验双升；仅探针触发的少数请求 +1 次调用 |
| 落点 | `pipeline.py` 步骤 6 后加反馈分支；`result_probe.py` 输出结构化反馈 |
| 成本 | 低 |

### C. 记忆类（补判据 D）

**方案 6：会话级记忆（Session Context）** ⭐ 当前完全空白、补上成本最低的一维

| 项 | 内容 |
|---|---|
| 做法 | API 层加 `session_id`，保存上轮 SQL/结果/探针提示，下一轮作为上下文注入 prompt；前端 Chat UI 获得真正的多轮能力（「那男性呢？」→ 复用上轮筛选条件） |
| 更像 agent | 跨轮记忆（判据 D） |
| 性能收益 | 追问类请求直接基于上轮结果，生成更准、甚至可跳过部分剪枝；不碰 eval 单轮路径 |
| 落点 | `api/routes.py` + `schemas.py` 加 session；`ask()` 加可选 `context` 参数 |
| 成本 | 低 |

**方案 7：意图指纹模板复用（Intent Fingerprint Cache）**

| 项 | 内容 |
|---|---|
| 做法 | 问句级缓存之上加「意图指纹」层：问句归一化（去掉数值/枚举值）后哈希，命中的模板只替换变量值（`年龄>{x}`、`等级='{y}'`），SQL 骨架直接复用 |
| 更像 agent | 模板记忆（判据 D 长期记忆形态） |
| 性能收益 | 相似问句从「全流程重算」变「变量替换」，延迟逼近纯缓存 |
| 落点 | `cache/keys.py` 扩展 |
| 成本 | 中（归一化规则需精心设计，误命中反而错；需与 `--no-exact-few-shot` 泛化轨开关联动） |

### D. 工具化与澄清类（最「agent」但代价最高）

**方案 8：预算化工具调用（Budgeted Tool-Use）**

| 项 | 内容 |
|---|---|
| 做法 | 仅对复杂档位暴露 2–3 个工具（`search_table` / `get_join_path` / `check_metric`），**硬性预算上限 2 次调用**，之后进入单发最终生成 |
| 更像 agent | 真正意义上的工具调用（判据 B）：模型自主决定查什么 |
| 性能收益 | 复杂查询中模型主动核验 join 路径/指标口径 → 准确率提升；预算封顶规避赛题「无限循环/多轮交互」痛点 |
| 落点 | `llm/chat.py` 支持 function calling（DeepSeek 已支持）；新模块 `agent/tools.py` |
| 成本 | 高（每次工具调用是完整 round-trip；需先验证 DeepSeek function-calling 稳定性），**优先级最后** |

**方案 9：低置信主动澄清（Clarify-on-Doubt）**

| 项 | 内容 |
|---|---|
| 做法 | 生成后加置信度门：检测到日期口径/指标口径/枚举含义歧义（模型低置信或确定性规则标记），返回「需要澄清」+ 2–3 个默认选项，而非猜一个答案 |
| 更像 agent | 多轮交互决策（判据 B/C） |
| 性能收益 | 消除「猜错重来」，模糊问句准确率提升；但牺牲单轮响应，与赛题「减少多次交互」有张力——只对低置信启用，且给默认选项一键确认（近似单轮） |
| 落点 | `pipeline.py` 增加 clarify 出口；`api/schemas.py` 返回 `needs_clarification` 标记 |
| 成本 | 中 |

### E. 系统级进化（让 agent「会学习」）

**方案 10：Eval 驱动的自动案例回流（Self-Evolving Loop）**

| 项 | 内容 |
|---|---|
| 做法 | eval 失败 → Eval-Agent 归因 → **自动把失败案例 + 归因转成 few-shot 样例**（写入候选区需人工确认）→ 下一轮 eval 自动验证提升。与 `logs/06` 提升点 2（半自动 Few-Shot 回流）衔接 |
| 更像 agent | 跨会话学习、能力自进化（判据 D+E 系统级形态） |
| 性能收益 | 每轮评测自动修正已知错误模式，准确率随迭代单调上升，直接服务「>90%」指标 |
| 落点 | `eval/runner.py` + `eval_agent.py` 输出到 few-shot 写入器 |
| 成本 | 低（复用现有 eval 基础设施） |

## 六、优先级与落地顺序

| 优先级 | 方案 | 更像 agent（判据） | 性能收益 | 成本 |
|---|---|---|---|---|
| **P0** | ③ 失败反思-重生成 | C/E | 准确率↑，成功路径延迟不变 | 低 |
| **P0** | ⑤ 探针反馈闭环 | B | 准确率↑，仅异常路径 +1 调用 | 低 |
| **P0** | ④ 多候选自洽 | C | 准确率↑↑，墙钟延迟不变 | 中（token×3） |
| **P1** | ⑥ 会话记忆 | D | 追问准确率↑，体验↑ | 低 |
| **P1** | ① 复杂度路由 | A | 简单问延迟↓，隔离复杂开销 | 低 |
| **P1** | ② 模型级规划-执行 | A/B | 复杂问延迟↓ + 准确率↑ | 中 |
| **P2** | ⑩ 自动案例回流 | D/E | 准确率随迭代↑ | 低 |
| **P2** | ⑦ 意图指纹缓存 | D | 相似问延迟↓↓ | 中 |
| **P2** | ⑨ 低置信澄清 | B/C | 模糊问准确率↑（与延迟有张力） | 中 |
| **P3** | ⑧ 预算化工具调用 | B | 复杂问准确率↑ | 高 |

**建议路径**：

1. **先做 P0 三件**：都在失败/异常路径上动手，成功路径零成本，却立刻获得「反思 + 反馈闭环 + 多尝试」三个 agent 特征。
2. **再做 P1**：会话记忆与复杂度路由补齐「记忆」与「决策权」两维，成本低。
3. **其余按答辩叙事需要选择性落地**。

做完 P0+P1，本项目即具备强 Agent 判据 A/B/C/D/E 的全部雏形，且每条快路径的延迟收益原封不动。

---

## 七、结论

1. 本项目是**确定性管道 + 受限 LLM 生成器**，属弱 Agent；强 Agent 5 条判据（决策权/工具循环/迭代/记忆/反思）全不满足。
2. **功能上不背离赛题**；形式偏离是「用确定性换确定性」的有意取舍，README/Summary 已有完整论证。
3. 真正的杠杆：**把「失败 / 复杂 / 模糊」这些原本浪费掉的路径变成 agent 的用武之地**——反思重生成、探针闭环、多候选自洽让每次失败都在赚钱；路由、记忆、规划让不同难度的问题享受不同深度的处理。**Agent 味加在错误和复杂上，性能赢在简单和成功上，两者不冲突。**
