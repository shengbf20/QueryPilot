### 部分 A：赛题分析与总体规划

#### 解决了什么问题

- 赛题要求构建 Agentic 智能问数系统，但初期只有原始数据和 README 规划，缺乏对**可行性、缺失资源、实施顺序**的清晰判断。
- 需确认：现有 8 张表是否足够、问答对在哪里、90% 准确率目标是否可达。

#### 解决方式

1. **对照赛题 README** 与 `data/` 实际内容，梳理数据分层（ads/dim/dwd/dws）及表间关系。
2. **识别风险点**：
  - 赛题描述 9 张表，实际只有 **8 张**（缺服务经理表、服务关系表）；
  - `ads_cust_info_d.data_dt = 20260531`，事实表日期不含该日，**跨表 Join 不能默认加 data_dt**；
  - `Q&A.xlsx` 即为问答对，可用于后续评测。
3. **确定技术路线**：Python 本地 Schema 剪枝 + 单次 LLM SQL 生成 + 双层安全围栏，替代多轮 Tool 循环以解决耗时长问题。
4. **项目命名**：**QueryPilot**（Agent 领航自然语言到数据洞察）。

2. `scripts/verify_db.py`：校验表行数、Join 可达性、EXPLAIN 语法；发现并确认**客户表与事实表日期不对齐**，验证脚本改为按 `pty_id` + 最新资产快照关联。
3. **数据完整性**：仅读取/复制 CSV，**未修改** `data/` **任何原始文件**。

### 部分 E：Step 1 — 8 张表 YAML 元数据

#### 解决了什么问题

- LLM 无法直接理解 `表描述.sql`；需 AI 友好的表别名、字段业务含义、同义词、营销场景说明。
- Agent Prompt 组装与 Schema 剪枝依赖结构化元数据。

#### 解决方式

- 在 `metadata/tables/` 为每张表编写 YAML，包含：
  - `alias`、`description`、`layer`、`primary_key`
  - 每列：`description`、`aliases`、`code_type_id`、`enum_ref` 等
  - `notes`：如日期不对齐约定
- 实现 `loader.py` + `validator.py` + `scripts/verify_metadata.py`。
- **检验**：字段集合与 `import_data.py` 中 DB schema 完全一致。

---

### 部分 F：Step 2 — Value Descriptor（编码字典）

#### 解决了什么问题

- 客户表字段（性别、学历、职业、等级、状态）存的是编码而非中文；
- LLM 若凭空猜测编码，会导致 SQL 条件错误。

#### 解决方式

**两层结构**（避免在 YAML 中维护 155 条 code）：

```
value_descriptors.yaml  →  声明列 → code_type_id 映射 + 静态枚举（sys_source/ccy/cust_type）
dim_public 表（DuckDB）  →  运行时加载 code → 中文描述
```

- 实现 `value_descriptors.py`：`resolve()`、`format_for_prompt()` 等 API。
- 实现 `value_validator.py`：交叉校验 + 客户表实际取值是否在字典中存在。
- **检验**：`scripts/verify_value_descriptors.py` + 7 个单元测试。

---

### 部分 G：Step 3a — Join-Graph 重构

#### 解决了什么问题

- 多表查询需正确 Join 路径；`dim_public` 需 5 条独立 lookup 边（各带 `code_type_id` 过滤）；
- 旧格式 `on: [gender_cd=code]` 不够规范，难以被代码解析。

#### 解决方式

- 重构 `metadata/join_graph.yaml`：
  - `join_rules`：全局约定（如 `no_default_data_dt`）
  - `edges`：规范 `join:` + `filter:` 格式，共 12 条边（含 5 条 dim_public lookup）
  - `paths`：8 条预定义多跳路径（如客户→持仓→产品）
- 实现 `join_graph_loader.py`、`join_graph_validator.py`。

---

### 部分 H：Step 3b — Join-Graph 路径引擎

#### 解决了什么问题

- Schema 剪枝需根据用户问题涉及的表，**自动补全中间关联表**并生成 JOIN 条件；
- 不能每次靠 LLM 推断 Join 路径。

#### 解决方式

- 实现 `join_graph.py` 中的 `JoinGraphEngine`：
  - `find_path(start, end)` — BFS 最短路径
  - `expand_tables(seeds)` — 连接多张种子表，补桥接表
  - `build_join_clauses()` / `format_join_clause()` — 生成 JOIN SQL（含 dim_public 的 code_type_id 过滤）
- **检验**：`scripts/demo_join_graph.py` + 9 个单元测试。

### 部分 I：Step 3c — 统一元数据校验

#### 解决了什么问题

- Step 1/2/3 各自有验证脚本，缺乏**一次性交叉校验**，无法保证三层元数据彼此一致。

#### 解决方式

- 实现 `metadata_validator.py` 中的 `validate_metadata_all()`：

## 六、解析 `metadata/` 与 `querypilot/metadata_engine/`

一句话：`**metadata/` 是「知识内容」，`querypilot/metadata_engine/` 是「读懂并使用这些知识的代码」。** 二者共同构成本项目三大模块中的「AI 友好元数据知识库」。

### 6.1 在项目中的位置

```
用户自然语言
       │
       ▼
┌─────────────────────┐
│  agent/（阶段二）    │  ← 取数 Pipeline：剪枝 → 生成 SQL → 执行
└──────────┬──────────┘
           │ 调用
           ▼
┌─────────────────────┐         ┌──────────────────────────┐
│ metadata_engine/    │ ──────► │ metadata/（YAML 配置）    │
│ （引擎 / 代码）      │  读取   │ （知识 / 数据）           │
└──────────┬──────────┘         └──────────────────────────┘
           │ 可选联动
           ▼
┌─────────────────────┐
│ db/ + dim_public    │  ← 编码字典的真实值在库里
└─────────────────────┘
```

- `metadata/` = 可运营、可编辑的**知识库内容**
- `metadata_engine/` = 把知识加载、校验、计算成 Agent 可用对象的**引擎**

### 6.2 各自负责什么

#### `metadata/` — 配置层（What：业务知识写在哪）


| 内容                       | 作用                                     |
| ------------------------ | -------------------------------------- |
| `tables/*.yaml`          | 每张表的别名、字段含义、同义词、编码字段标记                 |
| `value_descriptors.yaml` | 哪一列对应哪个 `code_type_id`；静态枚举（nm/fc、币种等） |
| `join_graph.yaml`        | 表怎么连、Join 规则、预定义多跳路径                   |
| `metrics/`、`few_shots/`  | 指标树、示例（预留，后续扩展）                        |


特点：

- **给人 / 业务运营改的**（改 YAML 不必改 Python）
- **无逻辑**：不自己算路径、不自己连库
- 对应赛题里的「可持续运营的 AI 友好元数据」

#### `querypilot/metadata_engine/` — 引擎层（How：怎么用这些知识）


| 模块                                       | 作用                                                  |
| ---------------------------------------- | --------------------------------------------------- |
| `loader.py`                              | 读 `tables/*.yaml` → `TableMeta`                     |
| `value_descriptors.py`                   | 读 YAML + 从 DuckDB 拉 `dim_public` → 编码解析 / Prompt 文案 |
| `join_graph_loader.py` + `join_graph.py` | 读 Join-Graph → BFS / `expand_tables` / 生成 JOIN 子句   |
| `*_validator.py`                         | 校验 YAML 是否与 DB schema、彼此一致                          |
| `bundle.py` → `load_metadata()`          | **统一入口**：一次给出 tables + values + join_graph + engine |


特点：

- **给 Agent / Schema Pruner 调用的 Python 代码**
- 负责解析、校验、路径计算、拼 Prompt 片段
- 不存放业务口径本身（口径在 YAML / DB 里）

### 6.3 怎么协作（一次典型调用）

```python
from querypilot.metadata_engine import load_metadata

md = load_metadata()
# 1. 引擎读 metadata/tables、value_descriptors、join_graph
# 2. 引擎再从 DuckDB 补 dim_public 的 code→中文
# 3. 得到 MetadataBundle，供后续剪枝 / 拼 Prompt / 校验 Join
```

数据流：

```
metadata/*.yaml  ──读──►  metadata_engine  ──产出──►  MetadataBundle
dim_public(DB)   ──读──►        │
                                ├── tables（表结构语义）
                                ├── values（编码↔中文）
                                ├── join_graph（拓扑）
                                └── engine（路径算法）
                                        │
                                        ▼
                              agent / Schema Pruner（阶段二）
```

分工对照：


|     | `metadata/`   | `metadata_engine/`      |
| --- | ------------- | ----------------------- |
| 本质  | 静态知识文件        | 可执行引擎                   |
| 谁改  | 业务/数据同学改 YAML | 开发改 Python              |
| 产出  | 人类可读的口径与拓扑    | 程序可用的对象与 API            |
| 依赖  | 不依赖代码         | 依赖 `metadata/`（+ 可选 DB） |


### 6.4 类比

- `metadata/` ≈ **词典 + 地图说明书**（表是什么、字段什么意思、怎么连）
- `metadata_engine/` ≈ **查词典、按地图找路的程序**（加载、校验、找 Join 路径、生成给 LLM 的 Schema 文本）

没有 `metadata/`，引擎没有知识可读；没有 `metadata_engine/`，YAML 只是文件，Agent 用不了。  
阶段二的 Agent 应只依赖 `load_metadata()`，一般不直接手搓解析 YAML。
