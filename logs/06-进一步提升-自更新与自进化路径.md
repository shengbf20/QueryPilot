# QueryPilot 阶段六：进一步提升——自更新与自进化路径探索

> 记录范围：基于 AI Agent 自更新/自进化技术，探索进一步提升准确率、迭代效率与系统鲁棒性的可行路径。  
> 记录时间：2026-08-12 规划落档  
> 状态：📋 规划中  
> 前置依赖：阶段二/三/四/五已完成；EX 评测体系可用；Few-Shot 回流机制已有人工闭环。

---

## 提升点 1：增强 Self-Debugging——按错误类型分级多轮纠错

**动机**

当前 L2 EXPLAIN 阶段仅允许 1-Shot 纠错（最多重试 1 次）。对于复杂查询，1 次纠错不一定够：例如第一次纠错修好了 Join 条件，但又引入了日期过滤错误。然而无限制多轮又会带来延迟和死循环风险。

**方案**

将纠错策略从"统一 1-Shot"改为 **"按错误类型分级"**：

| 错误类型 | 当前行为 | 增强行为 |
|----------|----------|----------|
| DB 报错（语法/列不存在/表不存在） | 1-Shot 纠错 | 保持 1-Shot（通常一次可修） |
| 空结果（EX=0 rows） | 结果探针提示 | 新增：自动回溯检查 WHERE 过滤条件，尝试放宽并对比，给出"放宽建议 + 差异行数" |
| EX 比对不一致（有金标时） | 归因报告 | 新增：针对高频错误模式（如 Join 遗漏、聚合口径偏差）做定向 2-Shot |
| 超时 / LLM 异常 | 优雅降级 | 保持降级 |

**关键约束**：总纠错轮次上限仍为 2（1-Shot + 可选 2-Shot），避免 ReAct 死循环。

**预期收益**：复杂查询（多表多指标）的一次通过率提升；空结果场景从"仅提示"变为"主动诊断"。

## 提升点 2：半自动 Few-Shot 回流

**动机**

当前 Few-Shot 回流完全依赖人工复核：评测失败 → 人工看归因 → 人工修正 SQL → 人工决定入库。这在高通过率阶段（如 Extra-A 36/36 已全过）效率尚可，但在泛化集扩充、问句变体增多后会成为瓶颈。

**方案**

引入 **"置信度分级自动回流"**，复用现有的人机复核分流逻辑但放宽自动通过的门槛：

| 置信度区间 | 当前行为 | 增强行为 |
|-----------|----------|----------|
| EX=100% 且置信度 > 85 | 自动标记通过 | **自动回流至 Few-Shot 候选池**（带来源标记） |
| EX=100% 且置信度 60–85 | 推送人工复核 | 保持不变 |
| EX < 100% | 进入 Bad Case | 保持不变 |

新增"候选池"概念：自动回流的条目先进入 `metadata/few_shots/candidates_auto.yaml`，与人工精选的 `examples.yaml` 分开存放。人工可定期审核候选池，择优合并入正式库。

**关键约束**：
- 自动回流条目带元数据标记（来源问句、EX 得分、时间戳），便于追溯和批量撤回。
- 候选池条目在 Prompt 组装时**可选启用**（通过 `--auto-few-shot` 开关），不影响默认行为。

**预期收益**：减少人工逐条入库的瓶颈；随着评测集扩充，Few-Shot 库可自动增长覆盖面。

## 提升点 3：DSPy 风格自动 Prompt/Few-Shot 组合优化

**动机**

当前 Few-Shot 选择策略有两种：精确匹配（`exact`）和 Top-K 相似（`fs3` / `fs0`）。哪种更好、选几条、用哪些样例，全靠人工经验和逐组评测。随着 Few-Shot 库增长，组合空间爆炸，手工试错不可持续。

**方案**

借鉴 **DSPy** 的"编译"思想，构建一个轻量级的 Prompt 配置搜索器：

```
输入：
  - Few-Shot 候选池 N 条
  - 评测集 M 题
  - 搜索维度：few-shot 数量(0/1/3/5)、选择策略(exact/bm25/embedding)、
    是否包含 CTE 规则提示、是否注入指标口径

搜索方式：
  - 网格搜索（小规模时）或贝叶斯优化（大规模时）
  - 优化目标：EX 准确率（主）+ 平均耗时（辅）

输出：
  - 最优配置 + 各配置对比表
```

**关键约束**：
- 搜索过程离线运行，不影响在线 `ask()` 路径。
- 搜索结果落盘为 `logs/prompt_search/` 下的 JSON 报告。
- 最优配置需人工确认后才切换生效。

**预期收益**：系统性替代手工 Few-Shot 调参；可在每次评测集扩充后重跑，自动适配新分布。

## 提升点 4：自反思记忆——Eval-Agent 归因结构化与检索复用

**动机**

Eval-Agent 目前已能输出 Markdown 格式的归因报告（错误类型、原因分析），但这些报告是"一次性"的——每次评测生成后就归档，不会被后续查询复用。实际上，很多失败模式是重复出现的（如"跨表误加 `data_dt`"、"公共维表漏匹配 `code_type_id`"）。

**方案**

将 Eval-Agent 归因结果结构化存储，并在 Schema 剪枝或 Prompt 组装时检索相关失败模式作为补充上下文：

```
归因记录结构：
  - error_type: "join_date_misuse"
  - pattern: "跨表 Join 时误加 data_dt 条件"
  - fix_hint: "跨事实表与维表只按 pty_id/org_id Join，不加 data_dt"
  - frequency: 出现次数
  - last_seen: 最近一次出现的评测批次

检索时机：
  - Schema 剪枝命中多表时 → 检索 Join 相关失败模式
  - 指标涉及日期过滤时 → 检索日期口径相关失败模式
  - 拼接到 Prompt 末尾作为 "⚠️ 已知陷阱" 补充
```

**关键约束**：
- 归因库只增不自动删（人工可清理），避免过时条目干扰。
- 检索命中数上限 3 条，避免 Prompt 膨胀。
- 此机制与元数据中的"日期不对齐说明"互补，不替代。

**预期收益**：将评测中积累的错误经验转化为在线查询时的防护知识，减少同类错误重复发生。

## 提升点 5：多 Agent 候选 SQL 投票（复杂查询增强）

**动机**

对多表多指标等复杂查询，单次 LLM 生成的 SQL 可能因"路径选择"不同而产生不同结果（如 Join 顺序、子查询拆解方式）。单一生成路径存在随机性风险。

**方案**

对**复杂查询**（由 Schema 剪枝阶段判定：涉及 ≥3 表或 ≥2 指标），启用多候选生成 + EX 投票：

```
1. 同一问句生成 2–3 个候选 SQL（调整 temperature 或用不同 Prompt 变体）
2. 分别执行，得到 2–3 个结果集
3. 两两 EX 比对：
   - 全部一致 → 高置信，直接返回
   - 2/3 一致 → 采用多数派结果，标记"中置信"
   - 全部不同 → 标记"低置信"，推送人工或降级提示
```

**关键约束**：
- 仅对复杂查询启用（简单查询不需要，避免浪费 LLM 调用）。
- 总延迟 = 并行生成耗时（可并发）+ 结果比对，控制在 2–3 倍单次耗时。
- 投票结果写入 `StageTiming`，供前端展示。

**预期收益**：复杂查询的准确率提升（多数投票天然过滤异常路径）；置信度信号可用于人机复核分流。
