### New Options

> 解读代码时发现的可选优化方向，均为非阻塞改进，按优先级粗略排序。

- `bundle.py` **惰性导入校验模块**：模块级 import `metadata_validator` 使整条校验链随进程启动加载，而 ask 热路径用不到；移入 `MetadataBundle.validate()` 内可省启动开销。
- `db/` **连接复用**：`get_connection` 每次新建只读连接，单进程高频 ask 可复用同一连接（eval 并发模式仍应各自开连接）。
- `llm/` **增加重试与超时封装**：LLM 调用失败目前直接上抛，仅靠 pipeline 的 try/except 降级；可加指数退避重试与超时，提升稳定性。
- **CLI 补充** `bench` **子命令**：文档（CLAUDE.md）提到 `querypilot bench`，实际入口只有 `scripts/bench_pipeline.py`，可对齐或改文档。
- **构建类脚本归位**：`data/extra`* 下的 `_build_*.py` 等一次性脚本与「data/ 只读」约定略冲突，可移入 `scripts/` 并规范命名（保留溯源价值，不建议删除）。
- **前端参数可配置化**：前端调 `/api/ask` 只透传 3 个参数、全走默认路径，与 eval 的可调参数（few-shot、缓存开关）不对齐；可考虑在 UI 或 API 暴露更多开关。


## 1. 项目总体目标（交付成果形式）



### 要解决什么问题

客户营销场景里，业务人员经常要按客户特征（等级、年龄、偏好等）和指标（资产、交易、持仓、收益等）做人群筛选与策略调整。传统方式要么依赖固化报表（不够灵活），要么要求业务人员懂 BI/SQL（门槛高），大量需求回流研发，取数周期长。

本项目要做的是一套 **AI Native 智能取数原型**：用户用自然语言提问，系统自动生成并执行安全的 SQL，在本地脱敏库上返回结果表。

### 量化目标（赛题口径）


| 维度   | 目标                                                         |
| ---- | ---------------------------------------------------------- |
| 响应时间 | 简单 / 中等 / 复杂查询均在**分钟级内**完成（工程上已压到秒级；重复问可缓存到毫秒～亚秒）          |
| 准确率  | 自然语言 → 真实执行结果的最终准确率达到工业可用标准（**>90%**，以 Execution Match 衡量） |
| 安全   | 拦截危险写操作与越权表访问，尽量减少幻觉列/幻觉表带来的影响                             |




### 交付成果形式（不是「一个 Prompt」）

最终交付的是一套**可运行、可评测、可运营**的工程闭环，而不是单接口 Demo：

1. **可运行的智能取数原型**：CLI（`querypilot ask`）为主路径；阶段五已提供 HTTP API + Chat UI 演示包装（盲测/文书打包后置）。
2. **完整源代码**：主包 `querypilot/`、可持续运营的 YAML 元数据 `metadata/`、测试与运维脚本。
3. **评测与证据材料**：金标 / Extra 评测报告、压测报告、过程日志（本目录 `logs/`）。
4. **元数据维护能力**：业务口径、指标、表关联、枚举字典可在 YAML 中扩展，无需改原始 CSV。

一句话：**交付的是「问数 Agent 系统」本身，外加证明它又准又快又安全的评测与文档。**

## 2. 项目难点

下面按「赛题卡点 → 本仓库真实踩过的坑」说明，便于理解设计为什么长成现在这样。

### 2.1 业务语言 ↔ 复杂数据结构的鸿沟

库里是按维度建模拆开的多张表（客户、资产、持仓、交易、产品、机构等），业务问句却是「近 30 日日均资产 > 100 万且买过某产品的女性」。模型需要同时搞对：

- 用哪几张表、哪些列；
- 指标怎么算（原子指标 vs 派生指标）；
- 枚举含义（如客户等级 A/B/C、风险偏好）；
- 表之间怎么 Join。

**难点不在「会写 SQL」本身，而在把企业约定口径稳定地塞进模型上下文。**

### 2.2 幻觉与不可信 SQL

大模型容易捏造不存在的表/列、写错 Join、误用日期过滤，或生成 `DELETE`/`DROP` 一类危险语句。仅靠「多轮 Tool 让模型自己查元数据」既慢又难控。

本项目的对策是：**Python 侧先剪枝出合法 Schema → 单次生成 SQL → 确定性围栏校验/修正**，而不是无限 ReAct 循环。

### 2.3 如何客观评价「取数准不准」

字符串比对 SQL 几乎无意义（写法不同、结果可能相同）。需要：

- 用**执行结果集匹配（Execution Match, EX）**做客观指标；
- 失败时能归因（漏表、口径、投影、别名作用域等）；
- 人工修正后能回流到 Few-Shot，形成迭代闭环。

实验上：官方金标曾从 **1/7（约 14%）** 提到 **7/7**；另用 Extra 改写集检验「关短路」后的泛化，避免只背原题。

### 2.4 数据与口径上的「隐藏地雷」（本仓库特有）

这些不是抽象难点，而是日志里反复出现的硬约束：


| 现象                 | 为何难                                       | 工程约定                                                |
| ------------------ | ----------------------------------------- | --------------------------------------------------- |
| 维表与事实表 **日期不对齐**   | `ads_cust_info_d` 的 `data_dt` 与事实表日期集合不一致 | 跨表默认只按 `pty_id` / `org_id` Join，**不要默认加** `data_dt` |
| 公共维表 `dim_public`  | 同一 `code` 可属不同编码类型                        | 必须同时匹配 `code` + `code_type_id`                      |
| 复杂营销口径（盈亏、Top-N 等） | 期间盈亏须减「期初 nm+fc」整体                         | `aset_pft = end−(bgn_nm+bgn_fc)+out−in`；Prompt / Few-Shot / `pnl_fix` 对齐（`logs/11`） |
| 准确率 vs 泛化          | 精确问句回流可「秒过」原题，改写后仍可能掉点                    | 评测分轨：默认轨（可开短路）与关短路 / Extra 泛化轨                      |




### 2.5 延迟：快，但瓶颈在 LLM

Schema 剪枝与围栏本身是毫秒～百毫秒级；端到端冷路径主要耗在 **单次 LLM 生成（及偶发 1-Shot 纠错）**。阶段四用缓存把热路径压到约数十毫秒，并用分阶段计时证明瓶颈位置——这对「体验性」评分至关重要。

### 2.6 为何不走「传统多轮 Tool Agent」

命题方已有经验：Tool 拉元数据能解决部分单表/多表问题，但**耗时长**，复杂题还要**多轮交互**。本项目刻意改成：

**本地隐式检索剪枝 + 单次 LLM SQL + 双层确定性围栏（失败最多纠错 1 次）**。

## 3. 项目架构



### 3.1 总体架构：三大核心模块

系统由 **三大核心模块** 构成（外围还有 LLM/DB、缓存、前端等支撑，但不单独算「第四大业务模块」）：

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      AI Native 智能数据洞察系统原型                       │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │
     ┌───────────────────────────────┼───────────────────────────────┐
     ▼                               ▼                               ▼
┌─────────────────────────┐ ┌─────────────────────────┐ ┌─────────────────────────┐
│  1. 高性能取数 Agent     │ │  2. AI 友好元数据知识库  │ │ 3. 自动化评测与复核平台   │
│  (Pipeline + Safety)    │ │   (Metadata Engine)     │ │   (Eval & Human-in-Loop)│
└─────────────────────────┘ └─────────────────────────┘ └─────────────────────────┘
```

三者关系可以记成：

- **元数据模块** = 神经系统（告诉 Agent「世界长什么样、口径是什么」）；
- **取数 Agent** = 核心大脑（把问题变成可执行、可校验的 SQL 并出数）；
- **评测模块** = 检验标尺（算准不准、错在哪、怎么回流改进）。

一次正常问数大致走：

```
自然语言（可选 history）
  → [Safety] 意图围栏：恶意指令直接 stage=safety，不剪枝、不调 LLM
  → [元数据] 加载 + Schema 剪枝（+ Join 补全；有 history 时拼上用户补充）
  → [Agent] 单次 LLM 生成 SQL；需求不清则 stage=clarify、空 SQL（CLI/对话可追问）
  → [Safety，挂在 Agent 流水线内] L1 AST → L2 EXPLAIN → 执行 / 1-Shot 纠错
  → 结果表（可选结果探针提示）
```

评测则在金标集上批量调用同一条 `ask()` 路径：普通题用 EX 对比结果集；Extra3 用「拒绝 + 安全警告」。

---



### 3.2 模块一：高性能取数 Agent

**一句话**：把自然语言变成「剪过枝的上下文 → SQL → 校验 → 执行结果」，并控制轮次与安全。

**核心功能**


| 能力          | 作用                                                           |
| ----------- | ------------------------------------------------------------ |
| Schema 剪枝编排 | 调用元数据引擎，只把相关表/列/指标送进 Prompt                                  |
| 单次 SQL 生成   | 组装规则 + Few-Shot + 口径，要求复杂逻辑用 CTE，输出结构化 JSON                  |
| 意图围栏        | 问句级拦截删库/改数/越权/越狱等；命中则 `stage=safety`，不进剪枝与生成           |
| 澄清 / 多轮     | 需求不清时 `clarify` 追问（`ok=True`、空 SQL）；`history` 注入后续一轮（有 history 时不走问句缓存 / exact 短路） |
| 双层安全围栏      | L1：sqlglot 静态拦写操作/越权表、修正列名幻觉；L2：`EXPLAIN` 试跑，失败则 **仅 1 次**纠错 |
| 结果探针        | 空结果或明显异常时给出交互提示                                              |
| 性能扩展        | 分阶段计时；查询/元数据缓存；可选多指标并行拆解（默认路径可不启用）                           |


**主要代码位置**


| 路径                   | 职责                                                 |
| -------------------- | -------------------------------------------------- |
| `querypilot/agent/`  | 主编排 `pipeline.py`（`ask()`）、Prompt、SQL 生成、部分确定性口径修复 |
| `querypilot/safety/` | 意图围栏、L1 AST、L2 EXPLAIN、结果探针（逻辑上属于 Agent 流水线的「护栏层」） |
| `querypilot/cache/`  | 阶段四：问数缓存、元数据缓存等                                    |
| `querypilot/llm/`    | DeepSeek 等 LLM 客户端                                 |
| `querypilot/db/`     | DuckDB 只读连接、`execute` / `explain`                  |
| `querypilot/cli.py`  | `querypilot ask` / `eval` / `bench` 等入口            |


**对应阶段**：阶段二（主链路）+ 阶段四（缓存/压测）；阶段五用 API/UI 包装同一套 `ask()`。

---



### 3.3 模块二：AI 友好元数据知识库（Metadata Engine）

**一句话**：用人类可维护的 YAML，把「表、指标、Join、枚举、样例」整理成模型友好、可剪枝的知识，并提供加载与检索。

**核心功能**


| 能力               | 作用                                            |
| ---------------- | --------------------------------------------- |
| 表级语义元数据          | 列说明、业务别名、场景描述（替代「只扔 DDL」）                     |
| 指标树（Metric Tree） | 原子/派生指标与计算公式，减少模型猜口径                          |
| Join-Graph       | 预存表关联与路径，剪枝时自动补全中间表与连接键                       |
| Value Descriptor | 枚举/编码含义（含公共维表使用约定）                            |
| Schema Pruner    | 按问句检索相关表列指标，压缩进 Prompt 的 Token                |
| 统一加载入口           | Agent **只经** `load_metadata()`（或等价封装），避免旁路读文件 |


**主要位置（配置 + 引擎）**


| 路径                                | 职责                             |
| --------------------------------- | ------------------------------ |
| `metadata/tables/`                | 逐表 YAML                        |
| `metadata/metrics/metrics.yaml`   | 指标树                            |
| `metadata/join_graph.yaml`        | 表关联拓扑（含日期不对齐说明）                |
| `metadata/value_descriptors.yaml` | 枚举值字典                          |
| `metadata/few_shots/`             | Few-Shot / 回流样例                |
| `querypilot/metadata_engine/`     | 加载、校验、Join-Graph、剪枝、指标与值描述辅助逻辑 |


**对应阶段**：阶段一建设；之后各阶段持续按评测归因增补口径与样例（**不改** `data/` 原始 CSV）。

---



### 3.4 模块三：自动化评测与人机复核平台

**一句话**：用「跑出来的结果是否一致」衡量 Agent，并把失败变成可归因、可回流的改进输入。

**核心功能**


| 能力                   | 作用                                                  |
| -------------------- | --------------------------------------------------- |
| 金标加载                 | 读取 `data/Q&A.xlsx` 等问答对，统一为 `question` / `gold_sql` |
| Execution Match (EX) | 执行 Agent SQL 与金标 SQL，比对结果集（对齐键、容差等）                 |
| 安全拒绝匹配             | Extra3：`eval_mode=safety_refuse`，金标 `SAFETY_REFUSE`；拒绝且带安全警告即算对（不跑金标 SQL） |
| Eval-Agent 归因        | EX 失败时输出错误类型与 Markdown 诊断，降低人工逐题排查成本                |
| 人机复核分流               | 高分自动过 / 模糊人工核 / 低分进 Bad Case；确认后回流 Few-Shot         |
| 延迟与压测配套              | 评测报告带耗时；阶段四另有冷/热路径压测报告                              |


**主要位置**


| 路径                                        | 职责                                    |
| ----------------------------------------- | ------------------------------------- |
| `querypilot/eval/`                        | 数据集、EX 比对、批量 runner、Eval-Agent、复核回流接口 |
| `scripts/baseline_eval.py` 等              | 一键基线 / Extra 复跑                       |
| `logs/eval_reports/`、`logs/perf_reports/` | 评测与压测产物（证据材料）                         |
| `data/Q&A.xlsx`、`data/extra*`、`data/extra3/` | 金标、泛化 Extra、恶意指令 Extra3（只读加载）      |


**对应阶段**：阶段三主线；续一/续二与阶段四续篇用同一套尺子做提准与泛化验证；阶段五盲测复跑复用报告叙事。
