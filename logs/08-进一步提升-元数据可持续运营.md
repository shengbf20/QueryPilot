# QueryPilot 阶段八：元数据可持续运营——同域新表自助接入机制

> 记录范围：面向赛题攻关任务 1「AI 友好元数据可持续运营」，设计「添加不含新主题域的表（类别 2）」的自助接入机制：自动化评测框架 + 人类问卷体系。
> 记录时间：2026-08-19 规划落档
> 状态：📋 规划中
> 前置依赖：阶段二~七已完成；`loader.py` 动态化重构（见 §四）；EX 评测与回归体系可用。

---

## 一、问题

赛题要求元数据**可持续运营**；当前添加新表需同时改动多处：

| 位置 | 现状 |
|------|------|
| `loader.py` `EXPECTED_TABLES` / `DB_COLUMNS` | 代码写死两份 schema 副本，validator 强校验强制同步 |
| `schema_pruner.py` 剪枝 cue / 白名单 | 新表不进 `_FACT_TABLES` / `_DOMAIN_SEED_CUES` 即永远选不到（FE09 教训：剪枝漏表 → L1 误杀） |
| `metadata/` YAML（table / join_graph / value_descriptors） | 每张表要手工写 |

**目标**：添加一张同域新表 = 人类只回答业务问题，全程不碰代码与机制文件；机器自动完成发现、落盘、注册、校验、回归。

**能力边界**：本机制覆盖**类别 2（同域新结构）**，顺带覆盖类别 1（同构表，改动更少）；**类别 3（新主题域）** 需要新领域知识注入，走「人工领域接入流程」，不在本机制范围。

---

## 二、难点

1. **语义无法自动生成**：列含义、粒度、join 语义、枚举含义是业务知识，库里只有列名，没有含义。
2. **列名同 ≠ 语义同**：`data_dt` 就是现成反例；新关系形状（非 `pty_id`/`org_id` 键、多对多）自动化只能给候选，最终判断必须人拍板。
3. **剪枝白名单机制**：同域继承 cue 依赖「人类正确选域」；选错域 → 剪枝与口径整体跑偏。
4. **人类确认环失效风险**：无脑全点「确认」会让猜测静默进系统；低置信项必须强制确认。
5. **LLM 错误不能直接进系统**：机制输入（YAML、注册表、join 边）出错即污染系统；LLM 只能给「建议」，不能写文件。

---

## 三、解决方案 / 添加功能（自动化评测框架 + 人类问卷体系）

### 3.1 总原则：知识由人注入，机制由机器执行

```
自动执行链（全代码，无 LLM）:  探数 → 骨架 → 键/枚举候选 → cue 继承 → 注册 → 校验 → 回归
        │                              ▲
        │ 组装候选                      │ 确认后落盘
        ▼                              │
人类确认环:  LLM 翻译候选为「业务问题 + 默认答案」→ 人类确认/修改 → （回填）
```

- **LLM 定位**：只把机械候选翻译成人类语言的问题与默认答案（如「`mgr_name` 看起来是服务经理姓名，对吗？」），**全部落在确认环内，出错无害**；去掉 LLM，流水线仍 100% 可运行。
- **代码定位**：探数、骨架生成、键/枚举候选、cue 继承、注册、校验、回归全为确定性代码；LLM 永远不直接写文件、不做机制决策。

### 3.2 自动化工作清单（全代码）

| # | 工作 | 输入 → 输出 |
|---|------|-------------|
| A1 | 结构自动发现 | `information_schema` → 列名/类型/键候选 |
| A2 | YAML 骨架生成 | A1 → 物理部分，描述留空 |
| A3 | 业务键候选 | 列名 ↔ 现有键集合（`pty_id`/`org_id`/`prdt_id`/`code`）匹配，带置信度 |
| A4 | 枚举候选 | distinct 探数 ↔ `value_descriptors.yaml` 值域比对 |
| A5 | 同域 cue 继承 | 人类选的「域」→ 自动挂剪枝 cue/白名单 |
| A6 | 注册表同步 | 目录扫描 → `EXPECTED_TABLES`/`DB_COLUMNS` 动态推导（需 §四 重构） |
| A7 | 自动校验 | 复用 `validator.py` / `join_graph_validator.py` |
| A8 | 自动回归 | 复用 `baseline_eval.py`：旧集回归 + 新表冒烟题；失败归因复用 Eval-Agent |

### 3.3 验收标准（DoD）

1. 添加一张同域新表：人类只答 ≤7 个业务问题，全程不碰代码/机制文件。
2. 旧集回归全绿（官方 7/7 + 双轨不回退）+ 新表冒烟题通过。
3. `EXPECTED_TABLES` / `DB_COLUMNS` 已动态推导，热路径代码零改动。

## 四、代码框架（设想新子包）

```
querypilot/table_ops/            # 元数据运维层，运行时零侵入（不被 ask/loader 引用）
├── __init__.py
├── discover.py                  # A1 结构发现 + A2 骨架生成
├── candidates.py                # A3 键候选 + A4 枚举候选（代码部分）
├── prompts.py                   # A9 LLM 生成业务问题/默认答案（可选 LLM）
├── register.py                  # A5 cue 继承 + A6 注册表同步 + 落盘
├── validate.py                  # A7 校验 + A8 回归编排（复用 validator / baseline_eval）
└── cli.py                       # 交互式「新表登记问答」入口（确认式表单）
```

**唯一必要的既有改动**：`loader.py` 的 `EXPECTED_TABLES` / `DB_COLUMNS` 改为由 `metadata/tables/` 目录 + 各 YAML 列定义动态推导（validator 强校验保留，清单不再手工维护）。其余热路径零改动。

**零侵入保证**：`table_ops` 单向依赖现有包（validator、join_graph、baseline_eval 产物），不被任何运行时模块反向引用；未来可经 `api/` 暴露为网页表单。

## 五、具体人类问卷内容

人类唯一接触的界面是「新表登记问答」，全部为业务问题，带自动默认答案，人类只做**确认 / 修改 / 填空**：

```
Q1 这张表是做什么的？            [默认: 从表名/别名推断] → 确认或改
Q2 它属于哪个业务域？            [默认: 按与现有表相似度排序] → 单选（客户/资产/持仓/交易/资金流/组织）
Q3 一行代表什么（粒度）？         [默认: 从键候选推断] → 客户级/账户级/持仓级/交易级/其他
Q4 以下列的含义对吗？            [列表: 列名 + 推断含义 + 确认框] → 逐列确认/修改/补充
Q5 以下关联关系对吗？            [列表: 候选 join 边 + 置信度 + 两侧抽样行数] → 确认/纠正/删除
Q6 以下列的值需要字典解释吗？     [列表: 值域与现有字典匹配的候选] → 确认；未匹配的填编码含义
Q7 有没有特殊口径要说明？        [可选: 一句话自然语言]
```

**接口 → 机制映射（使用者无感，机器自动转译）**：

| 人类回答 | 机器转译 |
|---------|----------|
| 选「客户域」 | 剪枝 cue / 白名单挂载（A5） |
| 列含义确认 | table YAML 的 description / aliases |
| 粒度确认 | join 边 cardinality + Prompt 聚合提示 |
| join 确认/纠正 | join_graph.yaml 的 edges / paths |
| 枚举含义 | value_descriptors.yaml / enum_ref |
| 一句话口径 | Prompt 规则（自然语言 → 规则模板） |

**防呆机制**：低置信候选（新键、值域不匹配）强制要求确认，不允许默认跳过；域选择给相似度排序默认 + 域代表题回归验证；回归失败翻译回业务语言反馈（如「这张表日期字段与客户表对不上，是否需要按日期过滤？」）。

**示例（补赛题欠账）**：添加「服务经理信息表 + 服务关系表」——A1–A4 自动探出 `pty_id`/`mgr_id`/`mgr_name` 等候选；人类答 Q1「客户服务关系表」、Q2「客户域」、Q3「客户级」、Q4 确认 `mgr_name` 含义、Q5 确认 `pty_id` 连客户表并纠正 `mgr_id` 为新键；机器自动写 YAML、注册、挂 cue、校验、回归 → 赛题 9 表清单补齐，人类全程只答 7 个业务问题。
