# 规划



## 一、 系统定位与总体交付目标

根据赛题的攻关任务与评分维度，本项目的最终交付物并非单一的 Prompt 或 API 接口，而是一套**工程化闭环的 AI Native 智能数据洞察系统原型**。系统以“高准确率、极速响应、强安全性、可持续运营”为核心设计准则，由以下三大核心模块构成：

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      AI Native 智能数据洞察系统原型                      │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │
     ┌───────────────────────────────┼───────────────────────────────┐
     ▼                               ▼                               ▼
┌─────────────────────────┐ ┌─────────────────────────┐ ┌─────────────────────────┐
│  1. 高性能取数 Agent    │ │  2. AI 友好元数据知识库 │ │ 3. 自动化评测与复核平台 │
│  (High-Perf Pipeline)   │ │   (Metadata Engine)     │ │   (Eval & Human-in-Loop)│
├─────────────────────────┤ ├─────────────────────────┤ ├─────────────────────────┤
│ • 动态 Schema 剪枝      │ │ • 指标树 (Metric Tree)  │ │ • Execution Match 引擎  │
│ • 单次 LLM SQL 生成器    │ │ • Join-Graph 拓扑图谱   │ │ • Eval-Agent 归因分析   │
│ • 双层确定性安全围栏    │ │ • Value Descriptor      │ │ • 主动学习与案例回流    │
└─────────────────────────┘ └─────────────────────────┘ └─────────────────────────┘


```

1. **核心大脑：高性能取数 Agent (High-Performance Agentic Engine)**

抛弃耗时严重的传统多轮 LLM Tool 循环，采用**Python 原生隐式检索 + 单次 LLM SQL 生成 + 双层确定性安全围栏**的高性能 Pipeline 架构，实现业务意图拆解、SQL 规划生成与结果自动纠错。
2. **神经系统：可持续运营的 AI 友好元数据知识库 (Metadata Engine)**  
包含指标树（Metric Tree）、数据表拓扑关联图（Join-Graph）与枚举值字典（Value Descriptor），解决自然语言与底层数据结构之间的转化鸿沟，支持业务人员后续可持续运营与口径扩展。
3. **检验标尺：基于 Execution Match 的自动化评测与人机复核平台 (Eval & Human-in-the-Loop Workbench)**  
以数据执行结果集匹配（Execution Match, EX）为核心评估指标，结合评测子 Agent（Eval-Agent）的归因分析与人机复核工作台，实现 Agent 准确率的持续衡量与自进化闭环。

## 二、 高性能 Agent 执行工作流架构

为解决传统 Agent “工具调用耗时长”与“复杂查询依赖多轮交互”的瓶颈，系统采用**单次 LLM 主驱动 + 代码级预处理/后校验**的工作流。端到端入口为 `querypilot.agent.pipeline.ask()`（CLI `querypilot ask` / HTTP `POST /api/ask`），**一次调用对应一次** `PipelineResult` **输出**（澄清后的追问是下一次调用，经 `history` 衔接）。

### 输入 → 输出契约


| 方向             | 内容                                                                                                                                        |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **Input**      | 中文自然语言问题 `question`；可选 `history`（`[{role, content}]`，澄清/多轮）；以及 `max_rows`、`max_few_shots`、`use_cache`、`use_parallel` 等                           |
| **Output（成功）** | `ok=True`：通常含 `sql`、`rationale`、剪枝命中的 `tables`、`columns` + `rows`、各阶段 `timing`；若结果为空/异常可能附带 `probe_message`（不阻断成功）。`stage=clarify` 时 `sql` 为空，`message` 为追问 |
| **Output（失败）** | `ok=False`、`degraded=True`：停在失败阶段 `stage`（`safety` / `prune` / `generate` / `l1` / `l2` / `execute`），`message` 说明原因；已生成的 `sql` / `rationale` 尽量保留供排查 |




### 端到端主流程（`ask()`）

下列为默认路径；**热路径缓存**与**规则并行**见后文「快捷分支」。

```
[用户自然语言 question]
       │
       ▼
┌─────────────────────────────────────────────────────────────┐
│ 0. 加载元数据（MetadataBundle，进程内缓存）                    │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 0b. 意图围栏  check_malicious_intent（问句 + 拼接后的 history）│
│     命中 → stage=safety，不剪枝、不调 LLM                      │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 1. Schema 剪枝  prune_schema / get_pruned_schema             │
│    问句扩展 → BM25 关联表/列/指标 → 领域 cue 补种子表          │
│    → Join-Graph 补全多表路径 → 输出剪枝 Schema 文本供 Prompt   │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. SQL 生成  generate_sql                                     │
│    ├─（可选）Few-Shot 问句完全匹配 → 直接返回已知 SQL，不调 LLM │
│    └─ 否则：组装 Prompt → DeepSeek 单次 JSON 输出            │
│       { sql, rationale, uses_cte, clarify? }               │
│       clarify 非空且 sql 为空 → stage=clarify，ok=True，停   │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 2b. 确定性 SQL 归一化（无 LLM）                               │
│     fix_period_pnl_sql（区间盈亏口径）+ fix_org_topn_sql（网点 Top-N）│
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. L1 静态围栏  guard_sql（sqlglot AST）                      │
│     拦截写操作 / 非授权表；列名模糊修正；失败 → 降级返回       │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 4. L2 动态围栏  validate_with_l2                              │
│     DuckDB EXPLAIN 预检                                       │
│     ├─ 通过 → 进入执行                                        │
│     └─ 失败 → 1-Shot LLM 纠错（附带 EXPLAIN 报错 + Schema）   │
│              → 纠错 SQL 再过 L1 → 再 EXPLAIN（最多 1 次纠错）  │
│              → 仍失败 → 降级返回（无 ReAct 循环）              │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 4b. 再次应用 2b 确定性归一化（L2 纠错后）                    │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 5. 执行  execute（DuckDB 只读，受 max_rows 限制）              │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 6. 结果探针  probe_result（空结果 / 计数为 0 / 异常量级）     │
│     生成交互提示与放宽建议；ok 仍为 True，message 可能 enriched  │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 7. 写入 Query Cache（成功且非降级路径）→ 返回 PipelineResult   │
└─────────────────────────────────────────────────────────────┘
```

**实现锚点**：`querypilot/agent/pipeline.py`（编排）、`sql_generator.py`（生成）、`safety/intent_guard.py`（意图围栏）、`safety/l1_ast.py` + `l2_explain.py`（围栏）、`safety/result_probe.py`（探针）、`cache/query_cache.py`（问句级缓存）。

### 快捷分支（在步骤 0 之前或替代部分主路径）


| 分支                 | 触发条件                                          | 行为                                                                               |
| ------------------ | --------------------------------------------- | -------------------------------------------------------------------------------- |
| **Query Cache 命中** | 相同问句 + 参数组合的缓存存在；**无** `history`            | 跳过剪枝/生成/围栏；直接回放已验 SQL；若缓存含结果行则毫秒级返回，否则重执行 + 探针                                   |
| **Few-Shot 精确短路**  | `allow_exact_few_shot=True`、无 `history`，且 HITL 回流样例问句完全一致 | 在步骤 2 内直接返回样例 SQL，不调用 LLM（评测泛化时可 `--no-exact-few-shot` 关闭）                       |
| **规则并行（可选）**       | CLI/API 传入 `use_parallel=True` 且问法命中多指标规则     | `parallel.try_parallel_pipeline` 拆成多条 SQL 并行执行后在 `pty_id` 上合并；成功则提前返回，失败则回退上述主流程 |




### 与旧版示意图的差异说明

- **L1 与 L2 分步执行**：L1 失败直接终止，不会进入 L2。
- **L2 纠错不回到「步骤 1 剪枝」**：仅在 L2 内部完成「EXPLAIN 失败 → 一次 LLM 纠错 → L1 → 再 EXPLAIN」；全程 LLM 调用上限为 **生成 1 次 + 纠错 1 次**（Few-Shot 短路与 Cache 命中时可为 0 次）。
- **步骤 6 探针与步骤 7 缓存**：原文档未体现；探针不阻止返回数据，缓存只写入围栏通过的成功路径。
- **步骤 0b 意图围栏 / 澄清出口**：恶意指令在剪枝前拒绝（`stage=safety`）；需求不清时生成步可停在 `stage=clarify`（空 SQL），由 CLI/对话带 `history` 再调一次 `ask()`。仍不是多轮 Tool/ReAct。

## 三、 详细实现步骤规划（全流程落地 SOP）



### 阶段一：AI 友好的“可持续运营”元数据与拓扑图谱构建

- **目标**：建立语义增强的元数据层，将大模型上下文 Token 压缩至最佳区间，消除业务语言与数据结构间的断层。
- **Step 1：元数据语义增强与业务口径建模**
  - 为 9 张表（客户表、资产表、持仓表等）添加业务别名、计算口径及业务场景描述。
  - **构建指标树 (Metric Tree)**：区分原子指标（如 `交易金额`）与派生指标（如 `近30日日均资产`），将复杂指标计算公式硬编码至元数据配置文件中。
  - **注入 Value Descriptor（值描述器）**：对 `客户等级`（A/B/C）、`风险偏好` 等枚举字段补充显式业务含义，减少 LLM 推理猜想。
- **Step 2：构建 Join-Graph 表关联拓扑图谱**
  - 将脱敏数据库的表间关系抽象为图结构（如 `客户信息表` --(1:N)--> `持仓表` --(N:1)--> `产品表`）。
  - 预存多表 Join 关联路径与主外键条件，避免 LLM 在复杂查询中遗漏 Join 关联键或拼错连接条件。
- **Step 3：实现代码级“上下文动态剪枝引擎 (Schema Pruner)”**
  - 编写 Python 检索模块，结合 BM25 关键字匹配与向量混合检索，在 **100ms 内**提取用户问题相关的核心表与指标。
  - 结合 Join-Graph 自动补全中间关联表，将全量元数据裁剪为仅包含当前查询所需的精简 Schema。
- **Step 4：沉淀营销场景 Few-Shot CoT 模板库**
  - 整理 30+ 常见营销场景（如“近3个月资产>100万且购买过A产品的30岁以上女性”），编写为结构化思维链（Chain-of-Thought）示例存入向量库。



### 阶段二：核心取数 Pipeline 与多层安全围栏开发

- **目标**：保证自然语言转 SQL 的准确率与安全性，彻底解决凭空捏造与幻觉问题。
- **Step 5：单次 LLM 驱动的 SQL 规划与生成器**
  - 组装 Prompt：包含剪枝后 Schema、计算口径、Few-Shot 示例及规则约束。
  - 针对多表多指标等复杂查询，强制要求 LLM 采用 **CTE（公用表表达式，WITH ... AS）** 结构生成 SQL，提升复杂逻辑的可读性与一次度生成成功率。
- **Step 6：L1 静态 AST 语法/逻辑安全围栏 (sqlglot)**
  - **高危拦截**：通过 SQL 语法树分析，直接阻断 `DROP`、`DELETE`、`UPDATE` 等写操作及非授权表访问。
  - **幻觉修复**：校验 SQL 中出现的列名是否在元数据中存在。若出现拼写微小偏差（如 `asset_bal` 写成 `asset_balance`），由 Python 代码自动模糊修正，无需重新调用 LLM。
- **Step 7：L2 动态 DB EXPLAIN 试运行与 1-Shot 精准纠错**
  - 将生成的 SQL 送入测试数据库执行 `EXPLAIN <SQL>` 进行语法与类型解析。
    - 若 DB 报错，捕获精确的错误日志（如 `Column X invalid`），拼接到 Prompt 中发起 **1-Shot 定向纠错**。若二次失败，则触发优雅降级提示，避免 ReAct 死循环。
- **Step 8：结果合理性校验与交互探针**
  - 当 SQL 执行成功但返回空数据（0 行）或数据严重偏离逻辑范围时，触发交互探针，主动给出提示（例如：“当前条件未检索到数据，是否需要取消‘30岁以上’限制？”）。



### 阶段三：自动化评测与人机复核平台建设

- **目标**：建立工业级自动化评估流水线，将人工审查工作量降低 80% 以上。
- **Step 9：基于 Execution Match (EX) 的自动化评测引擎**
  - 读取赛题提供的标注问答对，自动运行“生成 SQL”与“标准答案 SQL”。
  - 使用 Pandas/DuckDB 对比两组执行结果集的数据内容（校验 Key 对齐后的交集比率与数值偏差），计算出客观、绝对准确的 **Execution Match (EX) 准确率**。
- **Step 10：评测子 Agent (Eval-Agent) 归因分析**
  - 当 EX 比对不一致时，启动 Eval-Agent 分析错误类型（如：时间范围过滤偏差、Join 条件遗漏、聚合口径错误），并输出 Markdown 格式的诊断报告。
- **Step 11：主动学习人机复核工作台 (Human-in-the-Loop)**
  - **分级分流机制**：
    - **高分判定 (EX 100% / 置信度 > 85)**：自动标记通过，无缝入库。
    - **模糊区间 (置信度 60-85)**：推送至人工复核界面，提示人工确认或微调。
    - **低分判定 (置信度 < 60)**：直接驳回，进入 Bad Case 队列。
  - 人工修正后的优质 SQL 案例自动回流至 Few-Shot 向量库，实现 Agent 能力持续进化。



### 阶段四：系统性能压测与极速响应优化

- **目标**：优化端到端耗时，实现简单查询秒级响应、复杂查询十秒级完成（远超分钟级要求）。
- **Step 12：高频问数与元数据缓存 (Redis Cache)**
  - 对常见营销指标与高频取数模板设置 Redis 缓存机制，实现重复或相似查询的毫秒级直接返回。
- **Step 13：复杂查询任务并行拆解**
  - 针对跨主题域的多指标复杂查询，将计算拆解为“客户筛选子集”与“指标聚合子集”，在底层借助数据库并行计算能力提升响应速度。
